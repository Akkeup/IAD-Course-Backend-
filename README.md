## Лабораторная работа 2: база данных


Цель работы: разработка структуры базы данных и ее подключение к бэкенду
Порядок показа: Скриншоты 1-2 показать панель администратора adminer, в которой логически удалить через статус услугу, посмотреть данные через select в БД. Скриншоты 3-10 Показать 3 страницы приложения: выполнить поиск, удалить услугу, перейти по url удаленной услуги, добавить
услугу, показать select в БД, опубликовать карточку, снова показать select в БД. Скриншоты 11-13 В БД изменить поля по теме в услуге и количество строк в м-м и показать их в приложении. Скриншоты 14-21 В коде показать модели, 5 контроллеров через ORM, а удаление услуги через SQL
UPDATE. Скриншот 22 Фото и видео по-умолчанию в HTML
Контрольные вопросы: виды БД, SQL запросы, курсоры, ORM, модель и миграции, чистая архитектура
ER диаграмма: сделать в StarUML; таблицы, связи, столбцы, типы столбцов и их длина, первичные, внешние ключи
Задание: Создание базы данных PostgreSQL по теме работы, подключение БД к созданным трем шаблонам

Необходимо разработать структуру БД по выбранной теме и ее реализовать с учетом требований ниже. Использовать таблицу услуг в страницах разработанного приложения. Наполнить таблицы БД данными через Adminer.

Получение и поиск услуг, создание и публикация услуг (смена статуса) сделать через ORM. Для страницы плитки добавить кнопку логического удаления услуги (статус меняется на удален) с помощью выполнения SQL запроса UPDATE, без ORM. Всего шесть HTTP методов: три GET, один POST
добавления новой карточки через ORM, второй POST публикации карточки через ORM, еще один POST для удаления услуги через SQL курсор. При получении ленты от сервера БД должна возвращаться сразу только одна строка, не нужно выполнять фильтрацию в коде через массивы и тд.

Для создания нужно указать название, фото, видео, нажать кнопку Далее. Для публикации нужно заполнить краткую информацию, оба поля по теме и нажать кнопку Опубликовать. При отстутствии услуги в статусе черновик у пользователя, она создается только при нажатии кнопки Далее на
странице добавление. Если такая услуга уже есть, то страница открывается с заполненными полями и кнопкой Опубликовать. Новые фото и видел в этой лабораторной не сохраняются в БД и не передаются на сервер. Если в таблице пустые поля для url или файлы по ссылкам недоступны, то
отображаются фото и видео по умолчанию, которые хранятся вместе с иконками на SSR сервере (они же отображаются на всех страницах для всех новых карточек). Удаленные услуги просматривать нельзя. Ставить лайки во второй лабораторной НЕ нужно, только отображать из БД.

Требования к БД:

Обязательно наличие 3 таблиц (каскадное удаление запрещено!):

услуг (наименование, краткое описание, статус черновик/опубликован/удален, url к изображению, url к видео, два поля по предметной области, дата создания datetime, создатель; дата формирования datetime)
лайки м-м пользователь-услуги (первичный и два внешних ключа)
пользователей

Обязательно наличие 3 услуг: черновик, удалён, опубликован. У каждого пользователя не более одной услуги в статусе черновик. Названия таблиц и их полей должны соответствовать предметной области.

Стек лабораторной работы: Rust, Actix-Web, Tera, SeaORM, SQLx и PostgreSQL.

Первый инфраструктурный шаг поднимает PostgreSQL и Adminer:

```sh
docker compose up -d postgres adminer
```

- PostgreSQL: `127.0.0.1:5433` (внутри Compose: `postgres:5432`), база `andromeda`, пользователь `andromeda`, пароль `andromeda_password`;
- Adminer: `http://127.0.0.1:8081`;
- в Adminer выберите систему `PostgreSQL`, сервер `postgres`, базу `andromeda` и указанные учётные данные.

При запуске backend SQLx автоматически применяет миграции из `migrations/`. Основная схема содержит три предметные таблицы без каскадного удаления:

- `andromeda_users` — пользователи каталога;
- `andromeda_stars` — карточки звёзд со статусами `draft`, `published`, `deleted`;
- `andromeda_likes` — связь многие-ко-многим между пользователями и звёздами.

Вторая миграция добавляет опубликованные карточки, один черновик и одну логически удалённую карточку. HTML-страницы работают от имени `andromeda_student`; другого пользователя можно выбрать через `ANDROMEDA_CURRENT_USERNAME`.

Запуск backend:

```sh
cargo run
```

Адреса трёх страниц:

- лента: `http://127.0.0.1:8080/andromeda-stars/first` или `/andromeda-stars/{id}`;
- добавление и публикация: `http://127.0.0.1:8080/andromeda-stars/draft`;
- плитка и поиск по расстоянию: `http://127.0.0.1:8080/andromeda-stars/grid?distance_kpc=20`.

В приложении ровно шесть предметных HTTP-обработчиков:

- `GET /andromeda-stars/{id}` — одна опубликованная звезда из БД;
- `GET /andromeda-stars/draft` — черновик текущего пользователя;
- `GET /andromeda-stars/grid` — плитка и поиск на стороне БД;
- `POST /andromeda-stars/draft` — создание черновика через SeaORM;
- `POST /andromeda-stars/{id}/publish` — публикация через SeaORM;
- `POST /andromeda-stars/{id}/delete` — логическое удаление чистым SQL `UPDATE`.

Получение, поиск, создание и публикация выполнены через SeaORM. Только удаление использует SQLx с ручным SQL-запросом. Пустые медиа-адреса заменяются файлами из `static/defaults/`; выбранные при создании файлы не имеют HTML-поля `name`, поэтому браузер не отправляет их на сервер.
